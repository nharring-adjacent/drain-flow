# Drain Flow

Implementations of [Drain](https://jiemingzhu.github.io/pub/pjhe_icws2017.pdf) starting with an extremely naive single level approach and building towards a hopefully highly efficient implementation using [DifferentialDataflow](https://github.com/TimelyDataflow/differential-dataflow) with arbitrary depth.

## What is drain?

Drain is a technique for parsing and grouping log lines using a fixed depth parse tree. Parsing happens in several stages, see the linked paper for full details but the general idea is that first we run a pass of domain specific regexs to eliminate fields with expected variation (think leading timestamps on a log file which convey nothing about the similarity of log content), then selects a parse tree based on the number of words/tokens in the message, and finally descending into a token tree of arbitrary depth.

At the bottom of the tree is a vector of potential log matches which are the same length and begin with the same N tokens (or matching wildcards). Each match is scored by comparing the token in each position and awarding a point for each match.

The top-scoring message is then evaluated against as score / length > threshold and either added as an example of the existing record or added as a new record. When messages are added as new examples an additional pass is done to find any non-matching tokens and replace them with wildcards.

## Benchmarks

This project includes a comprehensive benchmark suite to evaluate the performance of log processing, ingestion, and querying. The benchmarks utilize realistically generated log data for various common log types.

### Available Benchmark Suites

The following benchmark suites are available:

*   **`realistic_ingestion_benchmarks`**: Measures the performance of log ingestion for different backends (e.g., `SingleLayer`, `TwoStageDrain`). It tests how quickly logs can be processed and added to a `LogStore`.
    *   **Log Types Covered**: MySQL Slow Query, Ruby on Rails, Syslog, Kubernetes Service Mesh (JSON), Kubernetes Infra (klog).
    *   **How to run**: `cargo bench --bench realistic_ingestion_benchmarks`

*   **`realistic_query_benchmarks`**: Measures the performance of various query types against `LogStore`s populated with realistic data.
    *   **Log Types Covered**: MySQL Slow Query, Ruby on Rails, Syslog, Kubernetes Service Mesh (JSON), Kubernetes Infra (klog).
    *   **Queries Tested**: Includes time-range aggregations (`query_log_range_aggregation`) and LogQL-like line filtering (`execute_logql_query`) tailored to each log type.
    *   **How to run**: `cargo bench --bench realistic_query_benchmarks`

*   **`core_benchmarks`**: Contains micro-benchmarks for core algorithmic components of the log processing logic, such as similarity scoring and variable discovery.
    *   **How to run**: `cargo bench --bench core_benchmarks`

### Log Data Generation

The benchmark data is generated by specialized modules in `benches/generators/`. These modules produce diverse log entries that mimic real-world log characteristics for the covered types, providing a more accurate performance assessment than simplistic or purely synthetic data.

### Running All Benchmarks

To run all available benchmarks, you can use:
```bash
cargo bench
```
(This will run all targets defined in `Cargo.toml`, including any older benchmarks if they haven't been removed and the new ones.)
